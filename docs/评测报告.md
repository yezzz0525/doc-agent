# 检索评测报告

> 用 `tools/eval/run_eval.py` 跑出来的真实数字。
> 复现命令见文末。**所有数字都是实跑的，不是估的。**

---

## 一句话结论

**Recall@4 = 96%（24/25）**，检索层已经够用。
当前的主要问题不在「检不检得到」，而在**每次检索拉回来的内容太多**（实测单次 17920 字 ≈ 1.8 万 token），
这是 token 成本的真正来源，详见「发现的问题」。

---

## 主结果

| 指标 | 数值 |
|---|---|
| **Recall@4** | **96.0%**（24/25） |
| 平均延迟 | 150 ms |
| 中位延迟 | 136 ms |
| 最慢 | 236 ms |

### 按分类

| 分类 | 结果 |
|---|---|
| concept | 6/6 = 100% |
| compare | 4/4 = 100% |
| config | 5/5 = 100% |
| howto | 9/10 = 90% |

### 按难度

| 难度 | 结果 |
|---|---|
| easy | 6/7 = 85.7% |
| medium | 13/13 = 100% |
| hard | 5/5 = 100% |

**反直觉的点**：hard 反而比 easy 高。原因是 hard 题（如「SAML2 和 OAuth2 有什么区别」）
天然对应多个文档，**任一命中即算对**；而 easy 题如果是「概念相似但问的是别的事」，
反而更容易被同主题的兄弟文档（index 页、overview 页）抢走 top1。

---

## topK 的影响（这个对比直接指导了配置决策）

| K | Recall |
|---|---|
| 2 | 96.0% |
| 4 | 96.0% |
| 6 | 100.0% |

**结论：K 从 4 加到 6 只多对 1 道题（Q02），但上下文成本增加 50%。**
当前保持 K=4 是合理的——为了 4% 的提升让所有问答都多付 50% 的 token，不划算。

如果以后 Q02 那类「兄弟文档互相抢」的问题变多，再考虑调 K。

## 唯一失败的题

```
Q02 [easy] 打包成容器镜像时怎么减小体积？
   期望：027-packaging-container-images-efficient-images
   实际：053-packaging-container-images-index      ← 索引页抢走了 top1
         061-packaging-container-images-dockerfiles
         066-packaging-native-image-index
         061-packaging-container-images-dockerfiles
```

**原因分析**：知识库里有三篇文档讲容器镜像（index / dockerfiles / efficient-images），
检索「减小体积」时，index 页因为含「efficient images」字样被排到第一，
但它本身只是目录页，没有实质内容。

**这是知识库结构问题，不是检索算法问题。**
可选的改法：
1. 在 `index` 类文档的元数据里标注「本页为目录」，
2. 或加载索引时把 index 页的文本压短（只留标题和链接）
3. 或在 prompt 里告诉模型「index 类文档没有实质内容，要继续检索具体子页」

**注意 ReAct 已经自动缓解了这个问题**——真实问答时模型看到目录页会去点具体那篇，
所以 Q02 在完整 ReAct 链路下大概率能答对。评测集只测检索层，所以暴露了它。

## 发现的问题：单次检索拉回的内容太多

Trace 里的实测数据：

```
[TRACE] q=RestClient  RestTem it=1 tools=[searchSpringDocs] callMs=474 ctx=17920 fetched=17920
[TRACE] q=starter it=1 tools=[listKnowledgeBaseTopics]  callMs=879 ctx=2405  fetched=2405
```

**`searchSpringDocs` 一次拉回 17920 字**。原因很直接：
- 切分大小 800 token（`DocumentService` 第 220 行 `withChunkSize(800)`）
- 每次取 4 段（`DocSearchTool.TOP_K = 4`）
- 800 × 4 ≈ 3200 token，加上格式包装约 17920 字

### 这为什么值得优化

**它才是 token 成本的真正大头。** 对比一下：
- ReAct 迭代 2~4 轮，多花的「轮次」成本：约 0.0005 元（前面算过）
- 单次检索 17920 字反复进入后续每一轮的上下文：**每轮都在重复付费**

也就是说：**第 3 轮、第 4 轮时，那 1.8 万字又要重新传一遍。**
轮数越多，浪费越呈倍数放大。

### 三个可试的改法（都有代价，要用尺子量）

| 改法 | 预期 | 风险 |
|---|---|---|
| TOP_K 4 → 3 | 上下文降 25% | Q02 可能也一起丢 |
| chunkSize 800 → 500 | 上下文降 37% | 需要**重建索引**，且片段更碎可能降低准确率 |
| 加 rerank，只送前 2 段给模型 | 上下文降 50% | 要多一次模型调用（但可以用便宜模型） |

**改完必须重跑 `run_eval.py` 看数字。** 这就是评测集存在的意义——
改之前 96%，改之后如果掉到 90%，就别改。

## 一个重要的教训：ground truth 错了会伪装成系统在犯错

**第一版评测跑出来只有 52%。** 排查后发现——
**12 道「失败」里，有 12 道是我自己的标准答案写错了。**

我造题时按文档顺序**凭印象猜了文件编号**，比如以为 profile 文档叫 `067-using-profiles`，
实际是 `064-features-profiles`。而评测脚本忠实地报告「没命中」。

**这比系统 bug 更危险**：如果当时没深究，就会去「优化」一个本来没问题的检索，
把代码越改越差。

修正方式：写了个脚本校验每个 `expectFiles` 里的文件在 `tools/spring-docs/` 里**真实存在**，
然后逐题对照实际文件名改正。

**教训**：评测集本身也是需要校验的代码。
**标准答案错了，比没有标准答案更糟**——它会给出方向完全相反的结论。

现在的 `questions.json` 里所有编号都已校验过。

## 复现方式

```bash
# 1. 启动后端（IDEA 里跑，或命令行）
# 2. 跑评测
python tools/eval/run_eval.py                    # 默认 K=4
python tools/eval/run_eval.py --topk 2           # 对比 K 的影响
python tools/eval/run_eval.py --difficulty hard  # 只跑难题
python tools/eval/run_eval.py --show-failed      # 打印失败题的检索明细
```

**评测是零成本、零延迟的**（只查向量库，不调大模型），
因为用了 `GET /api/eval/retrieve` 这个只检索不生成的接口。
25 道题约 4 秒跑完。

> ⚠️ 如果连不上，检查是不是走了系统代理。脚本里已经显式禁用了代理
> （`build_opener(ProxyHandler({}))`），但如果你改成 requests 库要注意同样的事。
