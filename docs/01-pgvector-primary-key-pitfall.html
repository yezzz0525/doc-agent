Invalid UUID string —— pgvector 主键类型踩坑记录

doc-agent pgvector / PostgreSQL 2026-10-04 状态：已修复并验证

一、错误原文

2026-10-04T17:29:03.028 INFO  [nio-8081-exec-5] o.s.a.transformer.splitter.TextSplitter : Splitting up document into 2 chunks.
2026-10-04T17:29:03.203 ERROR [nio-8081-exec-5] o.a.c.c.C.[.[.[dispatcherServlet] : Servlet.service() for servlet
[dispatcherServlet] in context with path [] threw exception
[Request processing failed: java.lang.IllegalArgumentException: Invalid UUID string: 001-security-saml2.md#0

触发时机：页面点「加载文档」，正在把切好的片段写进数据库。

二、一句话结论

我给每个文档片段起了个"人话名字"当主键（001-security-saml2.md#0）， 但 pgvector 的主键列只认 UUID 格式（8f3a...-...-...）。名字塞不进去，所以报 invalid。

修法：把主键列类型从 uuid 改成 text，一行配置。

三、为什么会这样

要理解这个错误，得先认识三个"角色"。它们的 ID 规则各不相同：

角色它对 ID 的要求说白了
我的代码
DocumentService		 任意字符串都行 我给片段起名 文件名#序号，好认、好查、重复加载能覆盖
pgvector 组件
PgVectorStore		 默认只接受 UUID
（源码 convertIdToPgType()）		 它拿到字符串先当 UUID 解析，解析不了就抛异常
PostgreSQL
表 vector_store		 主键列类型是 uuid 数据库只认 32 位十六进制的标准 UUID 格式

打个比方：片段 ID 就像贴在档案袋上的标签。

  • 内存版 SimpleVectorStore = 一堆便利贴贴墙上，你想写"001-安全.md#0"随便写，没人会拦。
  • pgvector = 银行金库，每个格子有固定格式的电子标签机，只认 UUID。你递一张手写标签过去，机器"滴"一声报警 —— 就是你看到的 Invalid UUID string。

为什么我当初要起这种 ID

这不是随便起的。之前有个 bug：重复点「加载文档」，界面显示的片段数从 319 变成 638，看着像白白烧了双倍 embedding 额度。

排查后发现数据其实没重复（向量库用主键覆盖了），但计数器在做累加所以翻倍了。修完之后我顺手把主键也换成了"文件名#序号"这种稳定 ID —— 这样重复加载时，数据库看到同一个名字就走 ON CONFLICT DO UPDATE 覆盖，不会插出两条一模一样的向量。

这个设计在内存版和 pgvector 版都是对的，问题只在于 pgvector 的主键列默认是 UUID，跟我的可读 ID 冲突了。内存版一直没暴露，因为它的键本来就是字符串。

四、为什么我之前没测出来

我的疏忽：我做 pgvector 改造时只测了"启动"和"自动建表"，没测真实写入。

当时看到日志打印「表已建好、HNSW 索引已建好」就认为完成了。但 initializeSchema 建出来的是 id uuid 这类结构，只有真正 INSERT 一条带字符串 ID 的数据，才会暴露这个冲突。

教训：新增一个持久化后端，"能启动"和"能读写"是两件事，必须都测。 好在你点了「加载文档」，这个动作本身把问题逼出来了。

五、两种修法，我为什么选第二个

方案做法结果
① 改成 UUID 把文件名哈希成 UUID：UUID.nameUUIDFromBytes("001-...md#0".getBytes()) 能写进去，但表里全变成 3f2a9b1c-7e4d-... ，看不出这条向量属于哪个文件，调试和演示都很吃亏
② 主键改 TEXT
已采用		 建表时指定主键类型是文本，直接原样存 001-security-saml2.md#0 稳定 ID 原样保留，可读、可查、可核对，还顺手解决了 ① 的问题

改动的代价：主键字符串比 UUID 长一点，占用空间略多。但—— 对检索速度毫无影响，因为 HNSW 索引建在 embedding（向量）列上，跟主键类型没关系。

// RagConfig.pgVectorStore() 里加的一行
PgVectorStore.builder(jdbcTemplate, embeddingModel)
        .vectorTableName(vectorTable)
        .dimensions(dimensions)
        .idType(PgVectorStore.PgIdType.TEXT)   // ← 新增：主键用文本
        .distanceType(PgVectorStore.PgDistanceType.COSINE_DISTANCE)
        .indexType(PgVectorStore.PgIndexType.HNSW)
        .initializeSchema(true)
        .build();

连带要知道的一件事：改主键类型必须删表重建。 代码只会"建表"，不会"改表结构"（没有 ALTER）。当时表里正好 0 行，删了没成本。 如果表里已经有数据了，就要先导出来、drop 掉、重建、再导回去。

六、修复后的验证证据

1. 删旧表 → 重打包 → 启动（自动建新表）

docker exec -it doc-agent-pg psql -U docagent -d docagent \
  -c "drop table vector_store cascade;"

2. 新表结构：id 变成 text，HNSW 索引还在

                 Table "public.vector_store"
  Column   |     Type     | Nullable | Default
-----------+---------------+----------+---------
 id        | text          | not null |          ← 改成了 text
 content   | text          |          |
 metadata  | json          |          |
 embedding | vector(1024)  |          |
Indexes:
    "vector_store_pkey" PRIMARY KEY, btree (id)
    "spring_ai_vector_index" hnsw (embedding vector_cosine_ops)   ← 索引没受影响

3. 实测插入原来会报错的这种 ID

insert into vector_store (id, content, metadata)
values ('001-security-saml2.md#0', '测试内容', '{"source":"001-security-saml2.md"}');

INSERT 0 1                                     ← 成功

           id            | content
-------------------------+----------
 001-security-saml2.md#0 | 测试内容

4. 顺带查证：重复加载不会撞主键

PgVectorStore 的写入 SQL 是这样的（源码实测）：

INSERT INTO vector_store (id, content, metadata, embedding) VALUES (?, ?, ?::jsonb, ?)
ON CONFLICT (id) DO UPDATE SET content = ?, metadata = ?::jsonb, embedding = ?

确实是"覆盖"而不是"插入"，所以稳定 ID 的设计在 pgvector 下依然成立， 重复点「加载文档」不会产生重复数据。

七、你要怎么操作

  1. 在 IDEA 里点 Stop 停掉正在跑的后端（它还是旧代码，必须停）
  2. 点 Run 重新启动（会重新加载新编译的代码）
  3. 刷新页面，点「加载文档」
  4. 看到 PostgreSQL · pgvector · 表 vector_store · 319 个片段 就成了

八、举一反三：以后遇到"能启动但一用就炸"怎么查

  1. 先看异常类名和参数。这次的 IllegalArgumentException: Invalid UUID string: xxx 已经把"什么东西"和"哪个值"都告诉你了 —— xxx 就是出问题的那个 ID，比读一百行日志有用。
  2. 顺着参数找到源头。xxx 是我们代码生成的片段 ID，去 DocumentService.loadDocs() 搜 .id( 就找到了。
  3. 去看对方的要求。报错说"要 UUID"，就去看 pgvector 的默认配置 （DEFAULT_ID_TYPE = PgIdType.UUID），确认能不能改。
  4. 改完一定要测真实读写。建表成功 ≠ 能写数据。启动日志好看 ≠ 能用。

把主键设成可读的"文件名#序号"，还有一个额外好处： 以后想查"这条答案到底来自哪个文件的第几段"，直接 select id from vector_store where ... 就看到了，不用去翻代码猜 ID 规则。 这种"可读性"在面试里也能讲 —— 它说明设计时考虑了运维和排查，不只是跑通。
